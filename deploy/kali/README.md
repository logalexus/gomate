# Kali test deployment

Изолированный проект `gomate-lab`: Go-приложение, отдельная PostgreSQL, шлюз Docker-discovery и три мока (HTTP, TCP, gRPC). Моки создают только синтетические маркеры. gRPC реализует реальные unary/server-streaming RPC; анализатор сохраняет raw bytes и декодированные сообщения.

Текущий хост: `ssh kali@192.168.56.103`, каталог `~/gomate-test`. SSH работает по ключу. UI доступен напрямую: **http://192.168.56.103:65000**. Нагрузочный трафик идёт из `devops` (`192.168.56.102`, интерфейс `enp0s8`) в Kali (`192.168.56.103`, интерфейс `eth1`). SSH используется только для управления и проверки БД, не для транспортировки тестовых запросов.

Логин: `packmate`. Отдельный случайный пароль UI и пароль БД хранятся в `~/gomate-test/.env` с правами 600. Пароль SSH не используется для приложения. В этой рабочей папке локальная копия лежит в `.cache/kali.env`, вне Git.

| Контейнер | Протокол | Адрес внутри сети | Опубликованный адрес на всех IPv4-интерфейсах Kali |
| --- | --- | --- | --- |
| http | HTTP/1.1 | 172.30.77.10:8080 | 0.0.0.0:18080 |
| tcp | Строковый TCP | 172.30.77.11:9090 | 0.0.0.0:19090 |
| grpc | gRPC / HTTP/2 без TLS | 172.30.77.12:50051 | 0.0.0.0:15051 |

Анализатор захватывает `eth1` до Docker NAT и сопоставляет сервисы по локальному адресу `192.168.56.103` и опубликованным портам **18080 / 19090 / 15051**. Docker bridge отдельно не захватывается, чтобы не дублировать трафик. Схема protobuf: [echo.proto](../../bench/mock/echo.proto). Внутренняя сеть контейнеров — 172.30.77.0/24.

Приложение и БД ограничены каждое 1 CPU / 2 GiB. Каждый mock ограничен 1 CPU / 128 MiB. На текущей Kali 12 CPU и около 24 ГБ RAM, поэтому это функциональный и предварительный нагрузочный стенд, а не приёмочный профиль общей машины 8 CPU / 16 ГБ.

```sh
cd ~/gomate-test
docker compose ps
docker compose logs --tail=100 app
docker compose down  # сохраняет БД; -v удалит историю и настройки
```

Нагрузка запускается **на исходной машине devops**, из `/home/logalex/gomate`:

```sh
CGO_ENABLED=0 .tools/go/bin/go build -trimpath -o bin/mock ./bench/mock
python3 scripts/remote-bench.py --tag smoke --count 100 --rps 50
python3 scripts/remote-bench.py --tag mixed --count 2000 --rps 200
```

`--rps` задаётся на протокол: второй пример предлагает суммарно 600 unary-вызовов/с по HTTP/TCP/gRPC, дополнительно выполняются streaming RPC. `remote-bench.py` проверяет ответы клиентов, уникальные ответные маркеры в БД, ошибки генераторов и потери анализатора. `count.py` на Kali выполняет только чтение БД. Сохранение raw-маркеров не является подтверждением семантического декодирования gRPC. Данные отчётов сохраняются локально в `reports/kali-*.json`.

Образы собираются локально и переносятся через SSH (`docker save | ssh ... docker load`). В публичный registry ничего не публикуется. После обновления образа: `docker compose up -d --wait`.

Результаты выполненных прогонов: [reports/KALI.md](../../reports/KALI.md). Успешный smoke подтверждает работу всех трёх протоколов на уровне захвата байтов; более высокие профили выявили проблемы с генерацией/обслуживанием нагрузки, поэтому устойчивую производительность пока не подтверждают.

## Обновление функций

HTTP-контейнер теперь предоставляет также `/gzip?marker=...` и `/ws`; gRPC поддерживает gzip. Протоколы декодируются при включённом HTTP decode в сервисе, WebSocket — при включённом Parse WebSockets. Сквозная проверка: `python3 scripts/verify-features.py` с машины генератора. Полный отчёт новых функций — [reports/FEATURES.md](../../reports/FEATURES.md). Исторические отчёты не переписывались.

## Динамические настройки

В UI → Настройки можно менять LIVE-интерфейс и сроки хранения без перезапуска. Сервисы из Docker добавляются через «+ Сервис». Для discovery в `.env` нужен отдельный случайный `DOCKER_DISCOVERY_TOKEN` (24+ символа); socket Docker доступен только контейнеру `discovery`. Шлюз слушает localhost:65001 и предоставляет discovery, логи и разрешённые действия управления контейнерами. Подробнее: [SETTINGS.md](../../docs/SETTINGS.md), [проверки UI](../../reports/DYNAMIC_UI.md).
