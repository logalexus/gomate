# Мониторинг ресурсов GoMate

Вкладка **Мониторинг**: `/#/monitoring`. Развёрнута на тестовом стенде
`http://192.168.56.103:65000/#/monitoring` 15 ноября 2026.

- Хост: CPU, занятая RAM, сетевой приём/передача, занятое и доступное место на `/`.
- Контейнеры: CPU, RAM/лимит, скорости сети и блочного I/O, число процессов/потоков.
  Поиск по имени или образу, сортировка CPU/RAM/имя, страницы по 20 строк.
  Нажатие на имя открывает четыре графика выбранного контейнера под таблицей.
- Периоды: 5 минут, 15 минут, час. Пауза и ручное обновление.
  Значения графиков доступны мышью и стрелками клавиатуры.
- Светлая и тёмная темы; таблица прокручивается внутри своей области на узких экранах.

## Источники и смысл показателей

CPU хоста рассчитывается по разности `/proc/stat`: 100% означает все логические CPU.
RAM хоста — `MemTotal - MemAvailable`. Вместимость и свободное место относятся к
файловой системе корня хоста, а не к writable-слою discovery-контейнера.

CPU контейнера: разность `cpu_usage.total_usage` / разность `system_cpu_usage`,
умноженная на число CPU и 100; 100% означает одно логическое ядро.
RAM контейнера вычитает `total_inactive_file` на cgroup v1 или `inactive_file` на v2,
как [Docker CLI](https://docs.docker.com/reference/cli/docker/container/stats/).
Сетевые и дисковые графики показывают **байты в секунду**, рассчитанные по разности
счётчиков и времени замеров Docker. PID включает потоки ядра.

Сеть хоста суммирует интерфейсы без `lo`, `veth*`, `docker*`, `br-*`, `virbr*`;
имена включённых интерфейсов указаны над графиком. Это не универсальная дедупликация
bond/VLAN/tunnel-интерфейсов: при такой топологии суммарный трафик может учитывать
один пакет несколько раз. У контейнеров с host networking отдельные сетевые
счётчики Docker могут отсутствовать. Недоступный показатель отображается как `—`.
Первый замер и сброс счётчиков дают пропуск скорости/CPU, а не ложный ноль.
Остановленные контейнеры остаются в таблице без текущих метрик.

## Ограничения и стоимость сбора

Один фоновый сборщик в discovery обслуживает всех пользователей. Интервал — 5 секунд,
тайм-аут полного прохода — 4 секунды, до 4 параллельных запросов Docker Stats
с `stream=false&one-shot=true`. UI читает готовый снимок через
`GET /api/v2/monitor?minutes=15&container=<64-hex-id>` и не запускает сбор.
API приложения требует обычную авторизацию; шлюз — Bearer-токен.

История в памяти: максимум 720 точек на хост и контейнер; максимум 128 контейнеров,
выбранных по имени. При превышении лимита UI явно предупреждает. История удалённых
контейнеров освобождается, при перезапуске discovery вся история начинается заново.
Длительное хранение и экспорт не реализованы. В ответ включается история хоста и
только выбранного контейнера, а не все временные ряды. При сбоях записываются пропуски;
старый снимок при HTTP-ошибке сохраняется с предупреждением. Скрытая вкладка и уход
со страницы прекращают запросы мониторинга; пауза UI не останавливает сбор на сервере.

Для Linux discovery использует host networking и read-only bind mounts:
`/proc:/host/proc:ro`, `/:/host/root:ro`, Docker socket. Они добавлены в оба Compose-файла.
`MONITOR_HOST_PROC` и `MONITOR_HOST_ROOT` позволяют указать другие пути при запуске
вне Compose. Без монтирований показывается ошибка источника, метрики контейнера
не выдаются за показатели хоста. Мониторинг не записывает данные в PostgreSQL.

## Проверки

```sh
.tools/go/bin/go test -race ./internal/monitor ./internal/dockerui ./internal/api ./cmd/discoverer
npm --prefix web run build
node tests/browser/monitoring.cjs
node tests/browser/monitoring-live.cjs
```

Последняя команда использует `.cache/kali.env` для авторизации на тестовом стенде.

Go: формулы CPU/RAM/скоростей, cgroup v1/v2, первые замеры и сбросы счётчиков,
отсутствующие mounts, кольцевая история, лимит контейнеров и параллелизма,
чтение во время сбора, очистка историй, зависший Docker/тайм-аут, авторизация,
валидация API и фиксированный one-shot запрос Docker. Проверка гонок прошла.

Браузер: управление таблицей, графиками и периодом; запоздавшие ответы API;
пауза/возобновление, ошибки и устаревшие данные; отсутствие метрик и пустой список;
8 сочетаний ширины экрана и темы, прекращение опроса после выхода.
Снимки JPEG с уменьшенным качеством.

На Kali: 20 контейнеров, 19 запущены; у всех запущенных получены RAM и статус без
ошибок сбора. Проверены реальные графики и рост истории. RAM хоста, число CPU и
вместимость `/` совпали с независимым чтением на хосте. 20 запросов снимка в 4 потока:
18–71 мс, среднее 38 мс. Это smoke-проверка API, не стресс-тест и не оценка предела
нагрузки. Захват работал весь период проверки без перезапуска.

Артефакты: UI (`monitoring-ui-check.json`, локальный артефакт), живой стенд (`monitoring-live-check.json`, локальный артефакт),
развёртывание и предыдущие образы (`monitoring-deployment.json`, локальный артефакт),
скриншот стенда (`monitoring-live.jpg`, локальный артефакт).

При развёртывании пересозданы только app и discovery. Остальные 17 запущенных
контейнеров сохранили image ID и StartedAt. Предыдущие образы и Compose-файл оставлены
на стенде для отката. Новый runtime-образ собран из scratch без старых слоёв приложения.
