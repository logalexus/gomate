# Динамическая конфигурация и управление шаблонами

Проверено 14 ноября 2026 на Kali `192.168.56.103`. Обновлённый UI: http://192.168.56.103:65000. Инструкция пользователя: [SETTINGS.md](../docs/SETTINGS.md).

## Реализовано

- Список интерфейсов хоста с IP и доступностью. Выбор LIVE-интерфейса, автоматические/ручные локальные IP, остановка и запуск capture через UI. Переключение не перезапускает HTTP-сервер или контейнер. Предварительная проверка нового socket сохраняет старый захват при ошибке.
- Настройки в PostgreSQL с проверкой версии при сохранении. При недоступном сохранённом интерфейсе UI продолжает работать. Сроки хранения меняются без перезапуска capture.
- Изолированный Docker-discovery gateway и список запущенных приложений с опубликованными портами. Добавление через «+» повторно проверяет актуальность порта и не перезаписывает существующий сервис.
- Отдельная автоматическая очистка payload и сессий, интервал, защита избранного. Ручная очистка всех сервисов или одного: оценка объёма, подтверждение, прогресс, отмена. Удаление малыми порциями; новый трафик за границей задания сохраняется. Задания переживают перезапуск.
- Менеджер шаблонов: поиск, группы, фильтры, массовые действия, переключатели, копирование, lookback. Полный редактор с пресетами, цветовыми вариантами и серверным тестером текста/HEX. При изменении условий создаётся новая версия, старые совпадения сохраняют исходный смысл.

## Проверки

`python3 scripts/test-integration.py` — успешно, включая `go test -race ./...` на отдельной БД `gomate_test`. `go vet ./...` — успешно. Docker image и production frontend собраны; Vite сообщает предупреждение о размере JS chunk, сборка завершается успешно.

Новые тесты проверяют подготовку/ошибку нового capture, сохранение старого reader при ошибке БД, отсутствие перезапуска при смене retention, корректное завершение reader; фильтрацию Docker-кандидатов; optimistic revision; защиту избранного, ручную и автоматическую очистку, сохранение нового трафика; тестер и массовое управление шаблонами, новые ID при смене условия, обязательное подтверждение удаления.

`node tests/browser/management.cjs` прошёл на развёрнутом образе. Машинный отчёт (`ui-management.json`, локальный артефакт):

1. Интерфейсы получены с реального хоста; `eth0 → eth1` переключены через UI. `StartedAt` контейнера остался прежним.
2. Отдельный временный Docker HTTP-сервис на `0.0.0.0:18081` добавлен через «+» без ввода имени и порта.
3. Созданы и проверены шаблон и группа; изменено условие; выполнены массовое выключение/включение, проверено состояние переключателя.
4. С машины генератора отправлены три HTTP-запроса на реальный адрес Kali. Все три сессии появились с совпадением нового шаблона.
5. Ручная очистка payload через UI удаляет содержимое двух обычных тестовых сессий, оставляя метаданные всех трёх и содержимое избранной.
6. Намеренный перезапуск приложения подтвердил сохранение выбранного интерфейса и retention в БД. Исходные настройки затем восстановлены; временные сервис, шаблоны и данные убраны.
7. Ошибок JavaScript нет. Шлюз discovery без токена возвращает 401; POST списка — 405; произвольный Docker endpoint — 404.

Скриншоты: хранение (`ui-storage.png`, локальный артефакт), Docker-сервисы (`ui-docker.png`, локальный артефакт), редактор (`ui-pattern-editor.png`, локальный артефакт), менеджер шаблонов (`ui-pattern-manager.png`, локальный артефакт).

После финального обновления выполнен `python3 scripts/remote-bench.py --count 100 --rps 10 --tag dynamic-smoke`. Отчёт (`kali-dynamic-smoke.json`, локальный артефакт): 100 HTTP + 100 TCP + 100 gRPC запросов, суммарно 30 unary/с примерно 10 секунд; дополнительно 10 streaming RPC / 30 ответных сообщений. Все 330 уникальных ответных маркеров сохранены. Ошибок клиентов, пропущенных генератором запросов, capture/queue/flow/write drops, ошибок декодирования и БД — 0. Трафик шёл `192.168.56.102 → 192.168.56.103`, без SSH-туннеля данных.

Это функциональная проверка и короткая проверка регрессий. Длительный soak, пиковая нагрузка и приёмка на общей машине 8 CPU / 16 GiB этим прогоном не подтверждаются. На Kali 12 vCPU и около 24 GiB; приложение и БД ограничены каждое 1 CPU / 2 GiB; discovery — 0.25 CPU / 64 MiB.

## Образ и данные

Проверка образов и отпечаток исходников (`dynamic-build.json`, локальный артефакт) подтверждает одинаковые RootFS layers локально и на Kali, соответствие запущенных app/discovery загруженному образу. Локальный image ID: `sha256:e5b3a3fd2c6a626de65a81ad2e8c00a4b289de7e52b830b668e4af7a6b5ecab5`. Remote ID отличается из-за сериализации image config при загрузке, слои одинаковы.

Перед обновлением сделана копия БД: `~/gomate-test/backups/before-dynamic-ui.dump`. Миграция добавляет таблицы настроек/заданий, признак очищенного payload и индекс. Существующие сервисы, шаблоны и история не удалялись вручную; автоматическая retention продолжает действовать по настройкам пользователя.

Для повторения браузерного теста требуется разрешённый Kali-стенд с mocks, SSH по ключу, локальный `bin/mock`, Playwright/Chromium и `.cache/kali.env`. Создайте только временный fixture; тест удаляет добавленную им конфигурацию и его данные:

```sh
ssh kali@192.168.56.103 'docker run -d --name gomate-ui-fixture --label gomate.ui-fixture=true --publish 0.0.0.0:18081:8080 --cpus .25 --memory 64m --read-only --cap-drop ALL gomate-mock:kali-test -protocol http -address :8080'
node tests/browser/management.cjs
ssh kali@192.168.56.103 'docker stop -t 5 gomate-ui-fixture && docker rm gomate-ui-fixture'
```

Этот тест намеренно переключает capture и один раз перезапускает приложение для проверки сохранения настроек; запускайте на тестовом экземпляре.
