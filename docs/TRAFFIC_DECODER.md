# Декодирование при просмотре трафика

У каждого блока трафика есть кнопка **Декодировать**. Выделите нужное значение в текстовом представлении и нажмите её: откроется декодер только для выделения. Если ничего не выделено, используется весь блок. В режиме HEX открываются исходные байты в HEX без адресов и ASCII-колонки.

При открытии текстового фрагмента запускается **автопоиск**: он предлагает варианты JWT, Base64/Base64URL, HEX, URL-кодирования и JSON. Например, значение `JyBPUiAxPTEgLS0=` в query string или HTTP-заголовке покажет `' OR 1=1 --`. Автопоиск эвристический: он показывает только текстовые результаты и может пропустить нестандартное обрамление, короткое значение или бинарный блоб. Для них используйте ручной выбор.

## Ручные декодеры

| Режим | Вход и поведение |
| --- | --- |
| Base64 / Base64URL | Обычный и URL-safe алфавит, необязательный padding, пробелы/переносы между частями. Некорректные символы, длина и завершающие биты отклоняются. |
| JWT | Три части JWS/JWT, также `Bearer …`. Header и payload показываются отдельно; `iat`, `nbf`, `exp` — дополнительно как время UTC. Подпись не проверяется. Зашифрованный JWE не раскрывается. |
| URL | `%XX` → UTF-8. Символ `+` сохраняется. |
| Form URL | `%XX` → UTF-8, `+` → пробел. Полезно для `application/x-www-form-urlencoded`. |
| HEX | Пары `00–FF`, допустимы пробелы, общий префикс `0x`, последовательности `\xNN`. Адреса и ASCII-колонку hexdump нужно убрать. |
| JSON / JSON-строка | Форматирует JSON; строковый JSON снимает один слой экранирования `\uXXXX`, `\n`, `\"` и т. п. Строка должна быть в двойных кавычках. |

**Результат → вход** позволяет снять следующий слой. Для вложенного значения внутри JSON/JWT выделите только его содержимое в результате/payload и нажмите **Выделение результата → вход**. Есть отдельная кнопка **Payload → вход**, **Назад** и возврат к исходному фрагменту. Доступны восемь переходов; затем начните с нового фрагмента. Копирование сохраняет показанный текст, включая пробелы и переводы строк.

Декодирование не подтверждает подлинность или срок действия JWT. Разделение чтения claims и проверки подписи соответствует структуре [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html). Здесь JWT используется как материал для анализа захваченного трафика.

## Производительность и пределы

- Обработка выполняется в отдельном Web Worker браузера, без обращения к внешним декодерам и без отправки введённого текста на сервер.
- На вход — максимум 65 536 UTF-16 единиц (счётчик JavaScript); на результат — 256 KiB; JSON ограничен глубиной 32. Если полный блок слишком велик, выделите меньший участок.
- Автопоиск — максимум 512 пробных преобразований, 16 вариантов и 262 144 символа суммарного текстового результата. При достижении лимита показывается сообщение.
- Один запуск ограничен двумя секундами. Есть отмена; изменение входа, закрытие окна и уход со страницы прекращают worker. Данные не обрабатываются заново при каждом LIVE-обновлении.
- Бинарный результат показывается как HEX первых 4096 байт с явной пометкой сокращения. Копирование такого HEX берёт только показанный фрагмент; преобразование бинарного результата в текст не выполняется с заменой повреждённых символов.
- HTML и скрипты отображаются как текст. Исходные пакеты, их совпадения и настройки сервиса не меняются. Декодированный результат не сохраняется в БД и не участвует в серверном поиске шаблонов/lookback.

Это локальный инструмент разбора выбранных данных, а не дополнительный этап LIVE-анализа всех сессий. Сжатые и зашифрованные произвольные блобы требуют отдельного декодера; HTTP gzip по-прежнему обрабатывается существующим протокольным анализатором.
